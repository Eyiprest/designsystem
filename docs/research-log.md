# Research log

Every row below is a page or registry entry I opened or queried while building Steady. Date checked is the date I read it. If a source is not in this table, I did not read it.

| # | Source | Date checked | What I learned | How it affects the project | Decision it informed |
|---|--------|--------------|----------------|----------------------------|----------------------|
| 1 | [What's New in WCAG 2.2](https://w3.org/WAI/standards-guidelines/wcag/new-in-22/) (W3C WAI) | 2026-10-26 | WCAG 2.2 adds 9 criteria. At AA: 2.4.11 Focus Not Obscured (Minimum), 2.5.7 Dragging Movements, 2.5.8 Target Size (Minimum, 24 by 24 CSS px, with spacing and inline exceptions), 3.3.8 Accessible Authentication (Minimum). 4.1.1 Parsing is removed. 2.4.13 Focus Appearance is AAA, not AA. | The test target is the AA set. Focus appearance is treated as a design goal, not a pass/fail requirement. | Minimum control height of 40px (above the 24px floor). Focus ring is a two-colour ring. No test case for 4.1.1. |
| 2 | [Storybook: Accessibility testing](https://storybook.js.org/docs/writing-tests/accessibility-testing) | 2026-10-26 | The a11y addon runs axe-core. `parameters.a11y.test` can be `'off'`, `'todo'` or `'error'`. Only `'error'` fails CI. The `region` rule is off by default for isolated components. The docs say the addon catches only part of WCAG issues and that "Incomplete" results need manual review. | Every story runs with `test: 'error'`. I do not use `'todo'` to hide failures. The Incomplete tab is part of the manual checklist. | Storybook a11y addon plus the Vitest addon as the automated layer. |
| 3 | [Deque: automated testing study](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues) | 2026-10-26 | Deque reports automated tools covered 57% of issues on average, across more than 2,000 audits. The figure is by issue volume, not by WCAG criteria, and it is Deque's own data (Deque makes axe). | I will not describe a clean axe run as proof of accessibility. The report keeps automated and manual results in separate columns. | Test report structure, and the wording of limitations in the README. |
| 4 | [axe-core README v4.14.0](https://cdn.jsdelivr.net/npm/axe-core@4.14.0/README.md) | 2026-10-26 | axe-core covers WCAG 2.0, 2.1 and 2.2 rules. It returns "incomplete" where it cannot decide. JSDOM support is limited and the `color-contrast` rule does not work there. | Accessibility tests must run in a real browser, not JSDOM, or contrast is never checked. | Vitest browser mode with Playwright and Chromium. No jsdom dependency. |
| 5 | [React Aria: quality and testing](https://react-aria.adobe.com/quality) | 2026-10-26 | React Aria handles keyboard events, focus management, ARIA roles and screen reader announcements. It states testing with VoiceOver (macOS, iOS), JAWS, NVDA and TalkBack across several browsers. | It is a reasonable base for the interaction-heavy parts. Its own testing claim does not transfer to my styled version, so I still test mine. | React Aria Components for Dialog, Tabs, Select (custom listbox parts), Switch, Checkbox/Radio group, Toast. |
| 6 | [Radix Primitives: accessibility](https://www.radix-ui.com/docs/primitives/overview/accessibility) | 2026-10-26 | Radix follows ARIA authoring practices and manages focus, but says the developer must supply labels. It does not name the assistive technologies it tests with. | I compared both libraries. React Aria publishes a specific tested-AT list, Radix does not. | Chose React Aria over Radix. One headless library, not two. |
| 7 | [The WebAIM Million 2025](https://webaim.org/projects/million/2025) | 2026-10-26 | Across home pages: low-contrast text 79.1%, missing form labels 48.2%, empty buttons 29.6%. Pages with ARIA averaged 57 detected errors versus 27 without. The report says that gap does not prove ARIA caused the errors, since those pages are also larger. 4.5% of pages had `role="menu"`, and 35% of those had barriers. | Contrast and form labelling get explicit tests. I avoid `role="menu"` for site navigation. | Navigation uses a plain list of links inside `nav`. Contrast is checked by script, not by eye. |
| 8 | [GOV.UK Design System: Error summary](https://design-system.service.gov.uk/components/error-summary) | 2026-10-26 | Summary goes at the top of main, focus moves to it on load, each item links to its field (first field for radios and checkboxes), summary wording matches inline wording, inline error is referenced by `aria-describedby`. | Direct model for the form component. | Form error summary behaviour. Same wording in summary and inline. Radio group error links to the first radio. |
| 9 | [Primer: color accessibility](https://primer.style/foundations/color/accessibility) | 2026-10-26 | Targets 4.5:1 for normal text, 3:1 for large text and for input borders and selected-state marks. Says state must not rely on colour alone. | Matches WCAG 1.4.3 and 1.4.11. Confirms that form control borders need their own 3:1 check. | Separate `border.default` (3:1, for controls) and `border.subtle` (decorative only). Errors always include text. |
| 10 | [Carbon: accordion accessibility](https://carbondesignsystem.com/components/accordion/accessibility/) | 2026-10-26 | Carbon splits each accessibility page into built-in behaviour, design considerations, development considerations and a testing-status table. Accordion header is a button with `aria-expanded` and `aria-controls`. Accordions start collapsed. | Gave me the section order for component docs and the testing-status table idea. | Documentation template. Accordion uses native `button` plus `aria-expanded`. |
| 11 | npm registry queries (`npm view`) | 2026-10-26 | Current: react 19.3.1, storybook 10.6.3, react-aria-components 1.22.1, vite 8.3.5, vitest 5.0.5, axe-core 4.14.0, tailwindcss 4.3.3. TypeScript latest is 7.0.2 and its package has no `main` entry. Peer ranges for the Storybook, Vitest and Vite packages overlap. | TypeScript 7 does not expose the JS compiler API that Storybook's prop-table generator relies on. | Pinned TypeScript to 6.0.3. |
| 12 | Local environment check | 2026-10-26 | Playwright 1.64.1 cannot download Chromium here (network allowlist). A Chromium build for Playwright 1.63 is already installed. It launches as Chromium 153.0.8010.12. | Test environment is Chromium 153 on Linux. No Firefox or WebKit run. | Pinned `playwright` to 1.63.0. Recorded as a limitation. |
| 13 | npm registry and web search for names | 2026-10-26 | `steadyui`, `prestkit`, `tallykit`, `clearpath-ui`, `payrail-ui` return 404 on npm (unclaimed). `ledgerkit` is taken. A search for "Tallykit" surfaced "Tailkits UI", which is close in spelling. A search for "Steadyui" or "Steady UI" found no component library of that name. | Name collision check is limited to npm and one web search each. It is not a trademark search. | Project name: Steady (package `steadyui`). |
| 14 | npm registry: `@fontsource-variable/atkinson-hyperlegible-next`, `@fontsource/atkinson-hyperlegible-mono` | 2026-10-26 | Both are 5.3.0, licence OFL-1.1, so they can be bundled in an MIT repository. | Fonts ship from npm, so no third-party request at runtime. | Typeface: Atkinson Hyperlegible Next and Mono. |
